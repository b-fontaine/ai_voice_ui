Genesis Canvas

Une app Flutter desktop qui compose ses écrans pendant qu'on lui parle.

Le speaker dit « Prépare la release 3.4 ». Un modèle vocal temps réel confie la demande à un orchestrateur, qui appelle trois agents. Les agents décrivent l'interface en JSON (protocole A2UI) et Flutter l'affiche avec son propre catalogue de widgets. Le cas d'usage, « Release Copilot », aide à décider si une release mobile peut sortir, sur des données fictives.

Ce site accompagne le talk. Le code, les slides et la documentation sont dans le dépôt GitHub.

Parcours conseillé

Quatre étapes, de la vue d'ensemble au code. Comptez une vingtaine de minutes pour les deux premières.

  1. Voir comment les pièces s'assemblent

    Déroulez d'abord l'acte 1 de bout en bout : il montre tous les acteurs. Passez ensuite au flux GenUI pour le détail des messages, puis au flux vocal.

  2. Lire l'architecture

    La vue d'ensemble explique où tourne chaque composant. Le guide de la documentation produit propose un parcours par profil : développeur Flutter, développeur backend, agent IA.

  3. Ouvrir le code cité dans les schémas

    Chaque étape des schémas donne ses fichiers. L'app est dans apps/ et packages/, l'orchestrateur et les agents dans backend/, le catalogue de composants partagé dans contracts/a2ui/genesis/v1/.

  4. Lancer la démo chez soi

    Les commandes sont plus bas. Un contrôle sans micro ni coût permet de vérifier l'installation avant d'ouvrir une vraie session vocale.

Lancer la démo

Il faut Docker, Flutter (cible Linux desktop) et une clé API OpenAI. La clé reste dans un fichier .env à la racine, lu par le backend seul ; l'app ne la voit jamais.

git clone https://github.com/b-fontaine/ai_voice_ui.git
cd ai_voice_ui
printf 'OPENAI_API_KEY=sk-...\n' > .env

tools/demo/run.sh --check   # contrôle sans micro ni coût : pile Docker + app, capture d'écran, arrêt
tools/demo/run.sh           # backend, trois agents, puis l'app ; tout s'arrête à la fermeture

Une fois l'app ouverte, cliquez sur « Démarrer », puis enchaînez :

  • « Prépare la release 3.4 » · quatre composants apparaissent.
  • « Concentre-toi sur Android et compare avec la 3.3 » · les composants changent sur place, une barre d'actions s'ajoute.
  • Clic sur « Bloquer la release » · la checklist se met à jour et la voix confirme.

La voix est facturée par OpenAI à la durée de session ; le script arrête la pile Docker à la fermeture de l'app. Avec Task, task demo lance la même chose en laissant la pile démarrée, task demo:clean la supprime et task slides ouvre la présentation.

Ce que contient le dépôt

DossierContenu
apps/, packages/L'app Flutter : session voix, canevas, catalogue de widgets, design system.
backend/L'orchestrateur et les trois agents A2A, en Go.
contracts/Le catalogue A2UI partagé entre le backend et l'app, avec des exemples de messages.
slides/La présentation du talk (reveal.js), utilisable hors ligne.
product/La documentation du produit : exigences, écran, architecture, décisions.
knowledge/Une base de notes datées et sourcées sur la voix temps réel, GenUI, A2UI et les protocoles d'agents.
specs/Une fonctionnalité par dossier : spécification, plan, tâches, état.
tools/loop/La boucle de développement autonome et sa porte de qualité.

Ce que vous pouvez réutiliser

La base de connaissances. Les notes de knowledge/ ne dépendent pas de cette démo. Elles servent de point de départ pour un projet de voix temps réel ou d'interface générée.

La méthode de travail avec des agents de code. AGENTS.md fixe les règles du projet ; les skills de .claude/ obligent l'agent à consulter la documentation avant d'agir.

Le patron d'architecture. Un catalogue fermé de composants, validé côté serveur puis côté app, et une clé d'API qui reste dans le backend.
