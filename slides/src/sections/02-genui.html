Catalogue

Définir un composant du catalogue


final riddleCard = CatalogItem(
  name: 'RiddleCard',
  dataSchema: S.object(properties: {
    'question': S.string(description: 'La question.'),
    'answer': S.string(description: 'La réponse.'),
  }, required: ['question', 'answer']),
  widgetBuilder: (ctx) {
    final json = ctx.data as Map<String, Object?>;
    return RiddleCard(question: json['question'] as String,
                      answer: json['answer'] as String);
  },
);
final catalog = BasicCatalogItems.asCatalog()
    .copyWith(newItems: [riddleCard]);
  • name = valeur de component
  • schéma injecté dans le prompt
  • builder = votre widget du DS
  • catalogId : une URI, figée par surface

Sécurité

Injection de prompt et protections

Le risque d'injection

  • chaque saut est une surface : voix → orchestrateur → agents → UI
  • une consigne cachée dans une donnée (un avis client…) détourne le modèle
  • l'UI générée peut alors mentir : faux formulaire, lien piégé

Notre approche dans ce projet

  • catalogue fermé, A2UI validé deux fois : orchestrateur puis app
  • retours d'agents traités comme données non fiables
  • aucune clé dans l'app : relais SDP par le backend
  • agents isolés : réseau interne, sans clé ; modèle via une passerelle de l'orchestrateur

Ces protections ont été prévues dès l'architecture, dans une démarche Secure by Design.

[ma-prompt-injection-tools] · [genui-a2ui-security] · [p-ar-security] · [rt-ephemeral-keys] · pdr-0053 · pdr-0074

Chaque saut = surface d'attaque · injection directe ou indirecte (avis client) Un exemple, sans garantie · validé 2 fois : orchestrateur, puis app Message refusé : aucune surface · marqué « refusé » dans le panneau protocole Voix : résumé de l'orchestrateur seulement · clic = événement typé Agents : réseau Docker interne, sans port ni clé · passerelle pour le modèle Prévu dès l'architecture, avant le code · plus dur à ajouter après
