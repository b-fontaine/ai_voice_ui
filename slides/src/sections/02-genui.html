Chapitre 02

GenUI & A2UI

L'interface générative côté Flutter

Deuxième partie : l'UI générative côté Flutter. On va voir ce qu'est GenUI, d'où ça vient, comment le moteur genui est construit, puis le protocole A2UI message par message : surfaces, composants, data model, actions, transports, sécurité. Point de vigilance pour tout le chapitre : genui est en alpha et A2UI en pré-1.0, les API bougent vite. Tout ce qui suit est daté d'octobre 2026 [genui-overview] [genui-a2ui-overview].

L'agent décrit l'interface en JSON ; le client la rend avec ses widgets

[genui-overview] · [genui-a2ui-overview] · [proto-a2ui-pointer] · [ux-genui-catalog-as-ds]

Le principe : l'agent envoie une description JSON déclarative, l'intention d'UI, que le client rend avec ses propres widgets. Aucun code Flutter ni HTML ne transite [genui-a2ui-overview]. genui laisse un LLM composer une UI Flutter à partir d'un catalogue de widgets approuvés, en parlant le protocole A2UI v0.9 [genui-overview]. Les rôles se répartissent ainsi : l'IA choisit quels composants et quelles données ; le développeur décide quels composants existent et à quoi ils ressemblent. L'agent se limite à des indications sémantiques, le style reste côté client [ux-genui-catalog-as-ds]. Le README d'A2UI résume l'objectif par « safe like data, but expressive like code » : la sûreté d'un format de données, avec une bonne part de l'expressivité du code.

Le terme « Generative UI » est introduit par Vercel avec l'AI SDK 3.0, le 1er mars 2024 : le LLM renvoie des React Server Components streamés, donc du code exécuté côté serveur (source : vercel.com/blog/ai-sdk-3-generative-ui). Le SDK existe avant son annonce : flutter_genui 0.0.1 est publié sur pub.dev le 2025-07-28. Le 2025-11-12, le paquet est renommé : genui 0.5.0 paraît le même jour que la dernière flutter_genui, 0.5.0, marquée « discontinued » et remplacée par genui (source : API pub.dev, consultée le 2026-10-29). Le 18 novembre 2025, l'équipe Flutter annonce le GenUI SDK en alpha, « built around the upcoming A2UI protocol », inspiré par la mise en page visuelle de l'app Gemini (source : flutter.dev/blog/rich-and-dynamic-user-interfaces-with-flutter-and-generative-ui). Ces jalons d'avant 2026 viennent des blogs officiels et de pub.dev, pas de la base knowledge/. Le 15 décembre 2025, Google publie A2UI en open source, avec des renderers Lit, Angular et Flutter (source : developers.googleblog.com, « Introducing A2UI »). A2UI est sous licence Apache 2.0, avec des contributions de CopilotKit [genui-a2ui-overview]. Entre-temps, le format passe de v0.8 à v0.9 : discriminant plat « component », beginRendering devient createSurface [genui-migration-from-0-7]. genui 0.10.4 est publiée le 2026-09-29, genui_a2a 0.10.1 le 2026-07-20 [genui-overview]. Dernier jalon = statut constaté le 2026-10-26 dans le README d'A2UI, pas une date de sortie : v0.9.1 en production, v1.0 en release candidate, v0.8 legacy [genui-a2ui-overview] [genui-a2ui-v1-rc]. Le CHANGELOG de genui annonce une refonte en a2ui_core, a2ui_agent et a2ui_flutter [genui-overview] [genui-migration-0-10]. Dans notre cas, on a choisi d'épingler les versions exactes.

Le moteur genui 0.10.x

Architecture du package genui

[genui-architecture] · [genui-user-actions] · [genui-multiple-surfaces] · [genui-migration-0-10]

Depuis la 0.8, genui sépare trois rôles. Le SurfaceController est le moteur : il applique les messages A2UI, tient un DataModel par surface et connaît les catalogues. Le Transport, en général A2uiTransportAdapter, transforme le texte du LLM en messages. La Conversation est la façade qui relie les deux : c'est elle qui branche transport.incomingMessages sur controller.handleMessage [genui-architecture]. genui n'appelle aucun LLM lui-même : c'est votre callback onSend qui le fait, puis vous poussez chaque morceau de texte avec addChunk. Le parseur sépare texte libre et messages A2UI. Pour un message déjà parsé, par exemple issu d'un tool call, on utilise addMessage [genui-architecture]. Chaque widget Surface affiche une surface identifiée par son surfaceId, à l'endroit choisi par l'app [genui-multiple-surfaces]. Au clic suivant : la boucle retour. Une action utilisateur sort par controller.onSubmit ; Conversation appelle sendRequest sur le transport, qui appelle votre onSend, et le LLM répond [genui-user-actions] [genui-architecture]. Deux points d'attention : la méthode s'appelle sendRequest (la doc mélange avec sendMessage), et depuis la 0.10 les messages sont des types a2ui_core [genui-migration-0-10].

Protocole A2UI v0.9 · agent → client

Les messages de l'agent au client


{"version":"v0.9","createSurface":{"surfaceId":"main",

[genui-a2ui-messages] · [genui-a2ui-overview] · [genui-multiple-surfaces]

Exemple adapté de la spécification v0.9.1, avec « version » forcée à « v0.9 » pour genui (mis en forme sur plusieurs lignes pour la lecture ; sur le fil, un message = une ligne JSONL). Chaque message porte « version » et exactement une clé parmi createSurface, updateComponents, updateDataModel et deleteSurface [genui-a2ui-messages]. createSurface fixe le surfaceId et le catalogId pour toute la vie de la surface. updateComponents envoie une liste plate de composants ; l'un d'eux doit avoir l'id « root ». updateDataModel remplace la valeur à un chemin JSON Pointer. deleteSurface ferme la zone. Trois points à surveiller. Un : genui 0.10.x exige « version » : « v0.9 » exactement, alors que les exemples de la spec v0.9.1 portent « v0.9.1 » [genui-a2ui-overview]. Deux : le transport doit garantir l'ordre ; genui met en tampon les updates arrivées avant le create. Trois : un createSurface sur un id actif est une erreur, il faut d'abord deleteSurface [genui-multiple-surfaces]. MIME standard depuis la v0.9.1 : application/a2ui+json. Attention, la doc Flutter cite encore les noms v0.8 (surfaceUpdate, dataModelUpdate) [genui-a2ui-messages].

Structure

Des composants en liste plate

  • Simple à générer pour un LLM : pas d'imbrication profonde
  • Rendu progressif dès que root existe ; le reste arrive ensuite

[genui-a2ui-overview] · [genui-a2ui-messages] · [ux-genui-streaming-loading]

A2UI décrit l'interface comme une liste d'adjacence : une liste plate de composants, chacun avec un id, et les enfants référencés par id via child ou children [genui-a2ui-overview]. On y voit deux avantages. Pour le LLM, c'est plus simple à produire que des niveaux d'imbrication. Pour l'utilisateur, le rendu peut commencer dès que root est défini ; les enfants manquants peuvent arriver plus tard, dans d'autres updateComponents incrémentaux [genui-a2ui-messages] [ux-genui-streaming-loading]. Au clic, le composant « name » arrive et l'arbre se complète : c'est le rendu progressif. L'utilisateur voit l'interface se construire progressivement. Dans l'exemple précédent tout arrivait dans le même message ; la spec permet de l'étaler. Différence avec la v0.8 : le type de composant est un discriminant plat, "component": "Text", et non plus un objet imbriqué {"Text": {...}} [genui-a2ui-messages].

Structure et valeurs séparées

  • propriété = littéral ou {"path": "/a/b"}

  • mises à jour granulaires (/user/name) plutôt que tout le modèle

Binding bidirectionnel

  • la saisie écrit dans le modèle, sans LLM
  • retour à l'agent : context ou sendDataModel
  • éviter tout secret dans le modèle opinion

[genui-data-model] · [genui-a2ui-client-messages] · [ux-genui-streaming-loading] · [genui-a2ui-security] · [genui-a2ui-v1-rc]

Chaque surface a son DataModel observable. Une propriété de composant est soit un littéral JSON, soit un objet path, un JSON Pointer vers ce modèle. Seuls les widgets qui dépendent d'un chemin modifié sont reconstruits [genui-data-model]. Côté agent, updateDataModel remplace la valeur à un chemin ; sans value, la clé est supprimée [genui-data-model]. On a intérêt à faire des mises à jour granulaires, /user/name plutôt que tout le modèle [ux-genui-streaming-loading]. Côté utilisateur, TextField, CheckBox, Slider ou ChoicePicker écrivent directement dans le modèle : aucun aller-retour avec le LLM pendant la saisie. Le modèle ne remonte à l'agent que dans le context d'une action, ou à chaque message si createSurface a sendDataModel à true [genui-a2ui-client-messages]. C'est pourquoi notre recommandation interne est de ne mettre aucun secret dans le data model [genui-a2ui-security]. Des fonctions comme formatString, formatDate, required ou email s'évaluent côté client. Dans la v1.0 RC, le binding devient {"@path": …}, non supporté par genui 0.10.x [genui-a2ui-v1-rc].

[genui-user-actions] · [genui-a2ui-client-messages] · [genui-a2ui-security]

L'agent attache une action à un composant, par exemple un bouton avec action.event.name « confirm_rdv » et un context lié au data model [genui-user-actions]. Au clic, le widget émet un UserActionEvent. La Surface le propose d'abord à son ActionDelegate, qui peut le gérer localement. Sinon le SurfaceController l'émet sur onSubmit, et Conversation le renvoie au LLM via sendRequest, donc votre onSend [genui-user-actions]. Sur le fil, c'est un message action : name, surfaceId, sourceComponentId, timestamp et context, tous requis [genui-a2ui-client-messages]. À noter : context ne contient que ce que l'agent a déclaré. Un functionCall comme openUrl s'exécute localement, sans aller-retour. Notre recommandation interne : traiter une action comme un événement typé renvoyé à l'orchestrateur, plutôt que de l'exécuter directement [genui-a2ui-security]. Sans Conversation, il faut écouter onSubmit soi-même, sinon les clics sont perdus.

Catalogue

Définir un composant du catalogue


final riddleCard = CatalogItem(
  name: 'RiddleCard',
  dataSchema: S.object(properties: {
    'question': S.string(description: 'La question.'),
    'answer': S.string(description: 'La réponse.'),
  }, required: ['question', 'answer']),
  widgetBuilder: (ctx) {
    final json = ctx.data as Map<String, Object?>;
    return RiddleCard(question: json['question'] as String,
                      answer: json['answer'] as String);
  },
);
final catalog = BasicCatalogItems.asCatalog()
    .copyWith(newItems: [riddleCard]);
  • name = valeur de component
  • schéma injecté dans le prompt
  • builder = votre widget du DS
  • catalogId : une URI, figée par surface

[genui-custom-catalog-item] · [genui-catalog-ids] · [ux-genui-catalog-as-ds]

Un CatalogItem, c'est trois choses : un name, qui est la valeur de « component » dans le JSON ; un dataSchema écrit avec json_schema_builder ; un widgetBuilder qui construit votre widget [genui-custom-catalog-item]. Les descriptions du schéma sont injectées dans le prompt : on les écrit pour le LLM, le quoi et le quand. En pratique, il faut aussi nommer le nouvel item dans les fragments de prompt système. Le catalogId est un contrat nommé entre agent et renderer, une URI par convention. Le client annonce ses catalogues via supportedCatalogIds ; l'agent en choisit un à createSurface, figé pour la vie de la surface. En v0.9, une surface n'utilise qu'un catalogue [genui-catalog-ids]. Point d'attention : un catalogue étendu par copyWith garde l'id du catalogue basique si on ne passe pas de catalogId ; un agent distant ignorera alors vos items. En production, le catalogue reflète le design system : chaque item enveloppe un composant du DS et lit le thème ; on le versionne comme une API, avec une version majeure dans l'URI (recommandation interne) [ux-genui-catalog-as-ds]. Des widgets métier de haut niveau coûtent moins de tokens que des primitives (opinion) [genui-custom-catalog-item].

[genui-a2ui-transports] · [genui-a2a-connector] · [proto-agui-overview] · [proto-a2ui-pointer]

A2UI laisse le choix du transport et définit ce qu'il doit garantir : livraison fiable et ordonnée, délimitation des messages (lignes JSONL, frames WebSocket, événements SSE), support des métadonnées comme les capabilities, et un canal retour optionnel pour les actions [genui-a2ui-transports]. Binding A2A : un message A2UI est une Part de message A2A, les capabilities vont dans metadata, la session correspond au contextId. C'est ce que fait genui_a2a. Vérifié dans le code et par un essai de bout en bout le 2026-10-29 : JSON-RPC message/stream sur SSE, protocole A2A v0.3, en-tête X-A2A-Extensions avec l'URI de l'extension A2UI v0.9. La doc Flutter mentionne WebSocket, mais le code de genui_a2a utilise bien SSE [genui-a2a-connector]. AG-UI transporte les événements entre backend et app, dont les instructions d'UI générative [proto-agui-overview]. MCP livre l'A2UI comme sortie d'outil ou abonnement à une ressource. Le cas le plus simple : le LLM écrit le JSONL dans sa réponse texte et A2uiTransportAdapter le parse [proto-a2ui-pointer]. Recommandation interne pour la voix : le canal de données de la session temps réel ne transporte pas l'A2UI ; on passe par un canal séparé vers l'agent GenUI [genui-a2ui-transports].

Sécurité

Injection de prompt et protections

Le risque d'injection

  • chaque saut est une surface : voix → orchestrateur → agents → UI
  • une consigne cachée dans une donnée (un avis client…) détourne le modèle
  • l'UI générée peut alors mentir : faux formulaire, lien piégé

Notre approche dans ce projet

  • catalogue fermé, A2UI validé par l'orchestrateur
  • retours d'agents traités comme données non fiables
  • aucune clé dans l'app : relais SDP par le backend
  • agents isolés : réseau interne, sans clé

Ces protections ont été prévues dès l'architecture, dans une démarche Secure by Design.

[ma-prompt-injection-tools] · [genui-a2ui-security] · [p-ar-security] · [rt-ephemeral-keys]

L'injection de prompt reste possible. En multi-agent, chaque saut est une surface d'attaque, de l'utilisateur à l'agent vocal, à l'orchestrateur, aux agents A2A, jusqu'au client [ma-prompt-injection-tools]. L'injection peut être directe, par ce que dit l'utilisateur, ou indirecte : une consigne cachée dans un contenu externe, par exemple un extrait d'avis client dans nos données. Un modèle qui génère de l'UI peut alors afficher un faux formulaire ou un lien piégé [ma-prompt-injection-tools] [genui-a2ui-security]. Dans ce projet, j'ai essayé de montrer un exemple de sécurisation, sans prétendre à une garantie : un catalogue fermé de composants, et un orchestrateur qui valide chaque message A2UI (composants, propriétés, liaisons) avant qu'il atteigne l'app ; la validation côté client reste à décider (Q-71) [p-ar-security]. Les retours des agents sont traités comme des données non fiables : la voix ne reçoit qu'un résumé produit par l'orchestrateur, sans le texte brut d'un tiers [p-ar-security]. Aucune clé dans l'app : c'est le backend qui relaie la création de la session voix [rt-ephemeral-keys]. Et les agents tournent sur un réseau Docker interne, sans port publié ni clé OpenAI [p-ar-security]. Ce qui nous a aidés, c'est de prévoir ces protections dès l'architecture, avant la première ligne de code, dans l'esprit Secure by Design ; elles auraient été plus difficiles à ajouter ensuite.

Erreurs et UX

Gestion des erreurs de génération

plafonner à 2 ou 3 tours opinion

  • afficher l'UI au fil de sa construction
  • chargement en 2 temps, avec un libellé
  • ne pas montrer l'erreur LLM à l'utilisateur opinion
  • message simple + étape suivante
  • confirmer avant une action importante

[genui-error-reporting] · [ux-genui-errors-validation] · [ux-genui-streaming-loading] · [ux-ai-human-in-the-loop]

A2UI décrit une boucle prompt, génération, validation. Quand un message viole le schéma, le client renvoie un error standard, code VALIDATION_FAILED, avec le surfaceId, un JSON Pointer vers le champ fautif et un message. Dans genui 0.10.x, Conversation renvoie automatiquement cette erreur au LLM, qui se corrige au tour suivant [genui-error-reporting]. Mesuré le 2026-10-29 sur genui 0.10.4 : un composant hors catalogue ou un createSurface en double sont signalés ; un update sur une surface inexistante est silencieux, mis en tampon. Il vaut mieux plafonner les tours de correction : ai_voice_widget en autorisait 20, la recommandation interne est 2 ou 3 [genui-error-reporting]. Côté utilisateur, notre recommandation interne est de ne pas afficher l'erreur de validation ; on montre un état de chargement, puis un message générique si le plafond est atteint [ux-genui-errors-validation]. Chargement selon Cloudscape : deux étapes, traitement puis génération, toujours avec un texte visible ; rien sous une seconde [ux-genui-streaming-loading]. Erreurs en langage simple avec une étape suivante (Apple HIG), possibilité de reprendre la main (Google PAIR). Enfin, on demande une confirmation avant toute action importante [ux-ai-human-in-the-loop].

Elles peuvent se combiner : AG-UI peut transporter de l'A2UI

[proto-protocol-map] · [proto-mcp-extensions] · [proto-agui-overview] · [proto-a2ui-pointer]

Carte des protocoles : MCP, c'est ce que l'agent peut faire ; A2A, à qui il délègue ; AG-UI, comment il parle à l'app ; A2UI, ce qu'il affiche [proto-protocol-map]. MCP Apps : un tool déclare une ressource ui:// ; c'est une page HTML rendue par le host dans une iframe sandboxée, qui dialogue par postMessage. Donc du code exécutable, isolé, qui suppose un host web ou une WebView [proto-mcp-extensions]. AG-UI est un protocole d'événements entre backend agentique et frontend, né du partenariat de CopilotKit avec LangChain et CrewAI ; il ne décrit pas lui-même l'interface. Côté Flutter, il existe un SDK Dart communautaire, ag_ui 0.3.0 [proto-protocol-map]. Sa doc dit qu'A2UI et AG-UI « work well together » [proto-agui-overview]. La ligne « Flutter natif » est une recommandation interne : pour une app Flutter native, A2UI nous semble le choix le plus adapté ; MCP Apps n'aurait de sens que dans une WebView, au prix de la cohérence visuelle et de la sécurité [proto-mcp-extensions] [proto-a2ui-pointer].
