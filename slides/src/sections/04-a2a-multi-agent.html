Chapitre 04

A2A & architectures multi-agents

Faire collaborer plusieurs agents en sécurité

On a vu comment l'écran est généré et comment la voix circule ; il reste à faire travailler plusieurs agents ensemble. Le chapitre reste générique : A2A et les patterns multi-agents tels qu'ils sont documentés fin 2026. Fil conducteur : qui parle à qui, avec quel protocole, et où l'on garde la main sur la sécurité. → D'abord une carte des protocoles, car chacun couvre une frontière différente du système.

Les protocoles et leurs rôles

[proto-protocol-map] · [proto-agui-overview] · [proto-mcp-overview] · [proto-a2a-overview]

Ces protocoles se complètent : chacun couvre une frontière du système, et aucun ne remplace les autres. MCP (Model Context Protocol) : sa spec courante, la 2026-07-28, est devenue sans état. AG-UI, absent du schéma, relie un agent à l'app par des événements typés ; encore pré-1.0, il peut porter de l'A2UI. Dans la démo, A2A ne circule qu'entre l'orchestrateur et ses trois agents ; l'A2UI voyage dedans jusqu'au backend. ⚠ Confusion fréquente : A2A pour appeler un simple outil, ou MCP pour coordonner des agents autonomes. → A2A est le moins connu des quatre : on commence par sa pièce de base, la carte que chaque agent publie.

  • Découverte : une URL well-known
  • supportedInterfaces : un binding par entrée, la 1re préférée
  • capabilities : streaming, push, carte étendue
  • skills : ce sur quoi l'orchestrateur route
  • Signature optionnelle : JWS sur JSON canonique (JCS)
  • Aucun secret dans la carte publique

[proto-a2a-overview] · [proto-a2a-agent-card] · [proto-a2a-dart-sdk] · [p-ar-backend]

Un agent A2A est un serveur HTTP qui se décrit lui-même dans un fichier JSON, à une adresse connue d'avance. Lignes 2 et 3 : l'identité. Lignes 4 à 7 : où le joindre, en quel binding. Lignes 8 à 10 : streaming et extension A2UI. Lignes 11 à 13 : le skill. Ses tags (ligne 12) sont ce que l'orchestrateur compare à la demande pour choisir. C'est la vraie carte de notre agent Qualité, en Go avec a2a-go v2 ; chacun des trois agents tourne dans son conteneur. L'orchestrateur relit les cartes à chaque délégation : le choix des agents se fait en code, sans appel LLM. ⚠ Pas de securitySchemes ici : la démo tourne en local sans authentification (pdr-0041), donc rien à cacher.

La Task : une machine à états

[proto-a2a-task-lifecycle] · noms complets : TASK_STATE_*

Quand l'orchestrateur envoie une demande, l'agent ouvre une Task et publie son état au fil du travail. Le contextId sert de fil de conversation : plusieurs Tasks successives peuvent le partager. Dans la démo : SUBMITTED à l'arrivée, WORKING pendant que l'agent produit ses écrans, puis COMPLETED. Demande hors de son périmètre : REJECTED. Sur « Stop », l'orchestrateur envoie CancelTask et la Task finit en CANCELED. ⚠ Relier INPUT_REQUIRED à une question vocale et AUTH_REQUIRED à OAuth est une reco interne ; la spec n'en dit rien. → ↓ pour le détail (messages, versions, authentification, patterns, sécurité). C'est ici que A2A et A2UI se rejoignent : A2A est l'enveloppe, et l'A2UI voyage dans une Part data. Lignes 2 et 3 : qui parle, et l'id du message. Ligne 5 : une Part texte. Raison : au spike, genui_a2a (A2A v0.3) lisait l'A2UI dans les statuts et ignorait les artifact-update. ⚠ La spec conseille de ranger les résultats dans les Artifacts ; l'A2UI en statut WORKING est un choix du projet, issu du spike. → ↓ comment ces statuts arrivent à l'orchestrateur, un par un. [proto-a2a-streaming-push] · [proto-a2a-task-lifecycle] · [p-ar-backend]

La séquence affichée est celle de nos agents : l'orchestrateur reste connecté du début à la fin de la Task. SSE (Server-Sent Events) : un flux HTTP descendant, un objet par événement, dans l'ordre ; en 1.0, l'état terminal clôt. À chaque statut WORKING, l'orchestrateur valide l'A2UI contre le catalogue puis le relaie tel quel à l'app (WebSocket). Le résumé de l'Artifact part vers la voix, qui le restitue une fois les résultats reçus. ⚠ Nos agents n'annoncent que le streaming : le panneau push concerne un client mobile, absent de la démo. → ↓ bindings et versions, un écart qu'on a payé au spike. [proto-a2a-bindings] · [proto-a2a-overview] · [proto-a2a-go-v03-compat] · pdr-0045

Le piège principal d'A2A aujourd'hui est la version : la 1.0 est incompatible sur le fil avec la 0.3. Beaucoup de tutoriels et de SDK tiers suivent encore la 0.3. Un serveur peut n'exposer qu'un binding. SP-03 : message/stream donnait -32601 (méthode inconnue) ; sans en-tête A2A-Version, -32009 (0.3 demandée, 1.0 servie). Côté web, gRPC est écarté faute de HTTP/2 natif dans le navigateur ; il reste valable entre services backend. Depuis pdr-0045, A2A ne circule qu'entre processus Go, en v1.0 native, sans couche de compatibilité. → ↓ le spike en question. (→ : chapitre suivant)

[proto-a2a-security] · [proto-a2a-agent-card] · [proto-a2a-dart-sdk] · [p-ar-security]

A2A s'appuie sur des mécanismes d'authentification existants, déclarés dans la carte à la manière d'OpenAPI. La 1.0 a retiré les flows OAuth implicit et password, et ajouté le Device Code. Le SDK Dart communautaire a2a ne gère ni ces schémas (hormis HTTPS) ni la carte étendue. Dans la démo, l'isolement réseau en tient lieu : agents sur un réseau Docker interne, sans port publié ni sortie. ⚠ Le schéma du haut est une recommandation pour un vrai déploiement ; la démo n'en applique aucune flèche. → ↓ les patterns multi-agents et leur coût en voix. (→ : chapitre suivant)

Chaque saut LLM ajoute de la latence, et en conversation vocale elle se ressent tout de suite. Sources : Anthropic pour routing et orchestrator-workers ; OpenAI Agents SDK pour agent-as-tool et handoff ; ADK pareil. Dans la démo, le routage est codé sur les tags des cartes ; le seul LLM ajouté est le composeur de l'agent Qualité. Composeur : p50 1,79 s au banc pour un objectif de 1,5 s (NFR-02) ; 2 à 4 s en répétition, sur sept sessions. D'où le squelette des surfaces envoyé avant l'appel, gardé par le porteur (pdr-0078) ; NFR-02 reste à remesurer. → ↓ où tourne chaque agent. (→ : chapitre suivant)

Où tourne chaque agent

patron recommandé orchestrateur backend : ADR-0002 acceptée backend Go hexagonal : ADR-0003 acceptée

[ma-target-architecture] · [ma-where-to-run-agents] · [ma-realtime-handoff-limits] · [adr-0002-orchestrator-backend] · [adr-0003-backend-go]

Un seul agent vocal parle à l'utilisateur ; tout ce qui demande un secret ou une permission vit au backend. Pourquoi pas plusieurs voix qui se passent la main : en temps réel, un handoff garde le même modèle. Pour un autre modèle ou un agent backend, la doc OpenAI recommande la délégation par outil. Dans la démo, les « Agent(s) GenUI » sont nos trois agents A2A : chacun produit l'A2UI de ses surfaces (pdr-0036). Qualité, Voix du client et Livraison : un conteneur chacun. L'orchestrateur ne recompose rien, il valide et relaie. → ↓ plus il y a d'agents, plus il y a de sauts à protéger : la sécurité de bout en bout. (→ : chapitre suivant)

En multi-agent, le risque qui se multiplie est l'injection indirecte, cachée dans un retour MCP ou une réponse A2A. Origine des mesures : 1 règle du projet, 2 et 3 recommandations internes fondées sur l'OWASP, 4 doc GPT-Live. Démo : les agents n'ont pas la clé OpenAI ; le composeur passe par une passerelle LLM interne, filtrée par adresse. Hors périmètre : REJECTED, motif fermé, journalisé sans le texte. Le script check-compose.sh vérifie ces règles en CI. ⚠ Couper la voix n'arrête pas le backend : il faut annuler les Tasks, ce que fait « Stop » avec CancelTask. → ↓ observer et évaluer ce système.
