## Contrats
- **Catalogue** : `contracts/a2ui/genesis/v1/` fait foi (`catalog.json`, fixtures). Un test du client charge les quatre fixtures, substitue `${CATALOG_ID}` partout, et vérifie qu'elles passent `GenesisMessageValidator` et s'affichent dans le moteur avec le catalogue de l'app (garde contre toute dérive client/contrat).
- **Liaison de données** : les items lisent leur objet depuis le data model par `dataContext` (le chemin `/<surface>` du composant `root`) ; ils ne castent jamais `ctx.data` en littéral ([genui-custom-catalog-item], [genui-data-model]). La première tâche TDD (T10) fixe le mécanisme exact sur `KeyIndicator` avant les trois autres.
- **Trois temps (RG-02, RG-03)** : le squelette est le `defaultBuilder` de `Surface` jusqu'à `updateComponents`, puis l'état « sans donnée » de l'item jusqu'à `updateDataModel` ; le premier squelette se peint à la frame qui suit `createSurface` (aucun `await` ni animation d'entrée avant).
- **Validation côté client (pdr-0053)** : après `A2uiDecoder`, avant `CanvasBloc` : message refusé = écarté, compté, une ligne fermée au journal (code `bad_component`, `bad_property`, `bad_binding`, `bad_catalog`, `too_many_surfaces`, `too_large`), jamais le contenu ; le flux ne s'interrompt pas. Le rail et le panneau consomment le flux **brut** : un message refusé reste visible dans le panneau avec la marque « refusé » (montre la défense en profondeur).
- **Statuts** : `ok|risk|blocking` seulement ; un code inconnu → état neutre. Les libellés (`statusLabel`, `levelLabel`, `recommendation.label`, `decisionStatus`) sont des données affichées telles quelles, jamais comparées.
- **Rail et choix des agents** : l'identité d'un agent est son **nom d'affichage** (RG-29) ; le roster initial est vide jusqu'au premier `plan` (canevas vide, RG-01) ; après `plan`, les quatre rôles sont toujours affichés.
- **Remise à vide** : ordre (1) `StageResetRequested` ; (2) vidage local de chaque Bloc (`CanvasResetRequested`, `ProtocolFeedCleared`, étagère, agents, acte 1) ; (3) `POST /canvas/reset` au mieux, en parallèle, jamais bloquant ; les `deleteSurface` du backend qui reviennent ensuite sont idempotents côté `CanvasBloc` (surface absente : sans effet).
- **Propriété et DI** : tous les nouveaux Blocs sont créés ou résolus par la page (racine de composition), fermés dans l'ordre de `_shutdown`, après leurs sources ; aucun `getIt` ailleurs ; pas de fake dans `lib/`.
- **Horloge** : horodatage du panneau et des mesures = `AppClock` (pdr-0038).

## Risques
- **Liaison `data: {path}` dans un `CatalogItem`** (objet entier lié, pas un littéral) : mécanisme à confirmer sur `KeyIndicator` (T10) ; si le moteur n'offre pas de souscription à un objet, repli : lire le data model par `dataContext.subscribe(path)` ; arrêt et `Q-xx` si ni l'un ni l'autre ne tient.
- **Les acceptations existantes (V1 à V5bis, H-01 à H-03) s'appuient sur `Text`/`Column`** : leurs fixtures changent (catalogue fermé), les assertions restent équivalentes ; risque d'affaiblissement → la revue d'architecte vérifie le diff des `.feature` ; aucun scénario n'est supprimé ni désactivé.
- **Lisibilité 24 px × quatre surfaces sur 1920 × 1080** : grille 2 × 2 avec défilement interdit ; si un contenu déborde, réduction par le thème de scène (jamais sous 24 px) et ajustement du contenu, vérifié par la capture d'`app-smoke`.
- **Chaîne de rendu sous Linux** (CustomPainter, GStreamer déjà prérequis de genui) : couverte par `gate --full` et `app-smoke`.
- **RD-9** : tant que 007 n'est pas publiée, `main` reste incohérente entre app et backend ; la publication de 007 la lève.
- **Remise à vide côté Go** : les agents n'ont plus de mémoire par contexte (006) ; le registre de l'orchestrateur est la seule source de vérité, donc le vider suffit à ce qu'une nouvelle demande recrée les surfaces (test d'acceptation Go).
