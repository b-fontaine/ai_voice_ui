Chapitre 05

Genesis Canvas sous le capot

Écran, actes, architecture technique et agentique, flux de données, méthode

Dernière partie : on ouvre le capot du projet qui sert de fil rouge. Genesis Canvas est un livrable de conférence, pas un produit de production [pdr-0001-conference-demo-deliverable]. Le cas d'usage est Release Copilot : décider go / no-go pour la release 3.4 d'une app mobile fictive face à la 3.3, sur des données fictives figées [pdr-0003-use-case-release-copilot] [pdr-0005-frozen-fictional-dataset] [pdr-0034-app-name-release-copilot]. Message du talk, tiré de la fiche produit : l'agent ne génère pas du code, il génère de la donnée d'interface ; le développeur Flutter garde la main sur le rendu via son catalogue [p-readme]. Important : tout ce qui suit décrit l'état du dépôt au 29 octobre, en phase de cadrage et de spikes. Je signale à chaque fois ce qui est décidé, proposé ou encore ouvert.

Architecture technique · C4 niveau 2

Qui tourne où

p-ar-overview · pdr-0028 · pdr-0029 · pdr-0041 · pdr-0036 · [adr-0002-orchestrator-backend] · [adr-0003-backend-go]

À gauche, l'app Flutter desktop Linux, lancée en debug hors conteneur [pdr-0028-linux-demo-machine]. Elle ne porte que l'audio WebRTC, le rendu A2UI et la régie de scène [p-ar-overview]. Au centre, le backend Go hexagonal [adr-0003-backend-go] : l'orchestrateur et un conteneur par agent A2A, lancés par docker compose depuis ce dépôt, ports publiés sur 127.0.0.1 sans authentification utilisateur [pdr-0029-local-docker-compose-hosting] [pdr-0041-backend-in-this-repo-local-no-auth]. Un processus par agent est décidé [pdr-0036-real-a2a-agents-produce-a2ui] ; un conteneur par agent est un choix de conception. L'orchestrateur est côté backend dès le départ [adr-0002-orchestrator-backend] : la clé OpenAI ne quitte jamais le backend, elle vit dans un .env non versionné. La voix va directement de l'app à gpt-live-1 en WebRTC [pdr-0012-voice-provider-openai] ; le backend écoute la même session en sideband [rt-gpt-live-sideband]. Seuls GPT-Live et le LLM texte sortent de la machine. Le canal app-channel en WebSocket est une recommandation : pdr-0045 est proposée, pas acceptée, et la question Q-39 reste ouverte. Le LLM texte des agents n'est pas choisi (Q-17).

Deux piles, deux architectures

pdr-0018 · A2UI v0.9 · genui 0.10.4 Flutter à figer · Q-25 Go à figer · Q-46

p-ar-frontend · p-ar-backend · p-ar-stack · [arch-clean-fsd-combo] · [di-no-service-locator] · [ma-backend-sdk-go]

Côté Flutter : Clean Architecture combinée à Feature Sliced Design ; chaque slice suit Clean en interne et les features ne s'importent pas entre elles, elles se coordonnent par les ports de entities/session [arch-clean-fsd-combo] [p-ar-frontend]. Les noms de slices et de Blocs sont une proposition de l'assistant, encore à valider. Toutes les zones de l'écran lisent un seul flux d'événements de session. Bloc uniquement, pas de Cubit ; DI par constructeur, getIt n'est jamais appelé dans un widget ou un Bloc [di-no-service-locator] ; get_it et injectable arrivent en J2 avec le premier service [pdr-0044-di-deferred-to-j2]. Côté Go : architecture hexagonale ; chaque fournisseur est derrière un port, par exemple LiveProvider, parce que le package live d'openai-go est jeune [p-ar-backend] [ma-backend-sdk-go]. Les versions expérimentales sont épinglées exactement [pdr-0010-pinned-experimental-versions] : genui 0.10.4 et A2UI v0.9 sont une décision contrainte [pdr-0018-a2ui-v09-genui-0-10-4]. Flutter 3.47.8 est déjà épinglée par le harnais 000 et recommandée par l'assistant ; la décision formelle reste Q-25, ouverte [specs/progress.md]. Go, openai-go (v3.88.0 observée, ≥ v3.86 requise) et le reste : Q-46 [p-ar-stack].

Architecture agentique · pdr-0036

Un chef d'orchestre, des experts

Catalogue : Indicateur clé Courbe de tendance Sentiment des avis Checklist go/no-go Barre d'actions Liste des crashs

pdr-0036 · pdr-0013 · pdr-0014 · pdr-0023 · pdr-0037 · [ma-target-architecture] · [rt-gpt-live-delegation]

L'agent vocal gpt-live-1 est l'unique interlocuteur ; tout travail passe par une seule délégation vers l'orchestrateur [ma-target-architecture] [rt-gpt-live-delegation]. Voix « brise », instructions rédigées pour la démo [pdr-0037-voice-brise-delegated-instructions]. L'orchestrateur planifie la demande en tâches, choisit visiblement les agents utiles, et les appelle en parallèle [pdr-0013-orchestrator-visible-agent-selection]. Les agents sont de vrais serveurs A2A, un processus chacun ; chacun produit l'A2UI de ses surfaces, et l'orchestrateur valide contre le catalogue puis relaie sans recomposer [pdr-0036-real-a2a-agents-produce-a2ui]. La composition se fait par un LLM guidé par des exemples d'écrans attendus, sur catalogue fermé : ni LLM libre, ni écrans pré-écrits [pdr-0023-example-guided-composition]. Quel LLM : encore ouvert (Q-17). Le catalogue a six composants [pdr-0014-six-component-catalog] ; la Liste des crashs est disponible hors scénario principal. Dans Genesis Canvas, les clics reviennent à l'orchestrateur comme actions typées, jamais exécutés localement : c'est un choix du projet [genui-a2ui-security] [p-ar-security], GenUI permettant aussi des actions locales ; le mécanisme, UserActionEvent puis onSubmit, est décrit dans [genui-user-actions]. Le commentary, c'est-à-dire le texte que l'orchestrateur fait dire à la voix, suppose le mode de délégation client [rt-gpt-live-delegation] : Q-47 reste ouverte, à établir par le spike SP-02. Pendant que les agents travaillent, la voix ne dit que des commentaires génériques, puis le vrai résumé [ma-filler-acknowledgements] [ma-real-tool-results].

SP-03 vérifié pdr-0045 proposée : WSS maison Q-39 ouverte

specs/001-sp-03-a2a-go-genui · p-rm-spikes · [proto-a2a-go-v03-compat] · [genui-a2a-connector] · [genui-test-a2a-roundtrip]

Question du spike : un agent Go écrit avec a2a-go v2 peut-il streamer de l'A2UI vers genui_a2a côté Flutter ? Réponse vérifiée le 29 octobre : oui [specs/001-sp-03-a2a-go-genui]. Le piège : genui_a2a 0.10.1 parle A2A v0.3, message/stream. Le handler natif v1.0 d'a2a-go ne connaît pas les méthodes v0.3 : -32601 « method not found » sur message/stream, et -32009 sur SendStreamingMessage sans en-tête A2A-Version ; il faut monter le handler de compatibilité a2acompat/a2av0 [proto-a2a-go-v03-compat] [genui-a2a-connector]. Résultat : l'agent émet cinq événements SSE, de task submitted à completed en passant par createSurface, updateComponents et updateDataModel ; l'app rend la surface, le tap repart par connectAndSend et l'agent répond « validé ». Aucune glue supplémentaire [genui-test-a2a-roundtrip]. Attention à la portée : c'est prouvé par un test widget de bout en bout contre l'agent Go réel, processus et HTTP/SSE réels, mais avec un tap simulé, sur un client Flutter jetable ; ce n'est pas encore dans l'app. Autres pièges : sendEvent n'atteint jamais le flux du connecteur, les clics doivent passer par connectAndSend ; l'Agent Card perd url et preferredTransport si l'interface n'est pas déclarée en version 0.3. Conséquence : le risque technique est levé, mais le choix du canal app ↔ backend reste au porteur. L'assistant recommande un WSS maison ; pdr-0045 est seulement proposée, Q-39 est ouverte.
