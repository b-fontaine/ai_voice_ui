Chapitre 05

Genesis Canvas sous le capot

Écran, actes, architecture technique et agentique, flux de données, méthode

Dernière partie : on ouvre le capot du projet qui sert de fil rouge. Genesis Canvas a été conçu comme un livrable de conférence ; il n'est pas destiné à la production [pdr-0001-conference-demo-deliverable]. Le cas d'usage est Release Copilot : décider go / no-go pour la release 3.4 d'une app mobile fictive face à la 3.3, sur des données fictives figées [pdr-0003-use-case-release-copilot] [pdr-0005-frozen-fictional-dataset] [pdr-0034-app-name-release-copilot]. L'idée centrale, tirée de la fiche produit : l'agent produit une description de l'interface sous forme de données, et le développeur Flutter garde la main sur le rendu grâce à son catalogue [p-readme]. Important : tout ce qui suit décrit l'état du dépôt au 31 octobre : seize fonctionnalités livrées, de 000 à 015, et une première répétition au micro sur enceinte le 31 [specs/progress.md] [product/sources/2026-10-31-repetition-micro.md]. Je signale à chaque fois ce qui est décidé, ce qui a été observé en réel et ce qui reste à vérifier : les questions Q-79, Q-80 et Q-87, et la fonctionnalité 016, encore à concevoir.

Architecture technique · C4 niveau 2

Où tourne chaque composant

p-ar-overview · pdr-0028 · pdr-0029 · pdr-0041 · pdr-0036 · pdr-0045 · pdr-0060 · pdr-0074 · [adr-0002-orchestrator-backend] · [adr-0003-backend-go]

À gauche, l'app Flutter desktop Linux, lancée en debug hors conteneur [pdr-0028-linux-demo-machine]. Elle ne porte que l'audio WebRTC, le rendu A2UI, le journal du rejeu et la régie de scène [p-ar-overview]. Au centre, le backend Go hexagonal [adr-0003-backend-go] : l'orchestrateur et un conteneur par agent A2A, Qualité, Voix du client et Livraison, lancés par docker compose depuis ce dépôt ; seul l'orchestrateur publie un port, sur 127.0.0.1, sans authentification utilisateur [pdr-0029-local-docker-compose-hosting] [pdr-0041-backend-in-this-repo-local-no-auth]. Un processus par agent est décidé [pdr-0036-real-a2a-agents-produce-a2ui] ; un conteneur par agent est un choix de conception. L'orchestrateur est côté backend dès le départ [adr-0002-orchestrator-backend] : la clé OpenAI reste côté backend, dans un .env non versionné. La voix va directement de l'app à gpt-live-1 en WebRTC [pdr-0012-voice-provider-openai] ; le backend écoute la même session en sideband [rt-gpt-live-sideband]. Seuls GPT-Live et le LLM texte sortent de la machine. Le canal vers l'app est un WebSocket maison, app-channel, en diffusion seule ; les clics et la remise à vide arrivent par des routes HTTP [pdr-0045-app-backend-channel-wss-recommended] [p-ar-app-channel-contract]. Le LLM texte est un petit modèle OpenAI, gpt-6-luna, retenu après une mesure courte [pdr-0060-small-openai-text-model-guided-a2ui]. Les agents n'ont ni clé ni sortie réseau : ils l'appellent par une passerelle interne de l'orchestrateur [pdr-0074-012-llm-composer-gateway-crashlist-details] [p-ar-llm-composer].

Côté Flutter : Clean Architecture combinée à Feature Sliced Design ; chaque slice suit Clean en interne et les features ne s'importent pas entre elles, elles se coordonnent par les ports de entities/session [arch-clean-fsd-combo] [p-ar-frontend]. Dans le code : deux entités, catalog et session, et une feature par zone ou presque : voice_session, agent_activity, canvas, catalog_shelf, protocol_feed, replay, stage_controls. Toutes les zones de l'écran lisent un seul flux d'événements de session. On utilise uniquement Bloc, sans Cubit ; l'injection se fait par constructeur et getIt n'est appelé que dans la page racine de composition [di-no-service-locator] [pdr-0057-getit-composition-root-exception]. La fonctionnalité 013 a ajouté des tokens au format DTCG, générés en constantes Dart, et un catalogue visuel Widgetbook 4, en bêta épinglée [pdr-0075-013-design-ergonomics-details-assistant-decided] [pdr-0079-013-tokens-exception-to-adr-0005]. Côté Go : architecture hexagonale ; chaque fournisseur est derrière un port, par exemple LiveProvider, parce que le package live d'openai-go est jeune, ou LlmText pour le modèle de composition [p-ar-backend] [ma-backend-sdk-go]. Les versions expérimentales sont épinglées exactement [pdr-0010-pinned-experimental-versions] : genui 0.10.4 et A2UI v0.9 sont une décision contrainte [pdr-0018-a2ui-v09-genui-0-10-4] ; Flutter 3.47.8 [pdr-0046-flutter-3-47-8-pinned] ; Go 1.27.3 dans les go.mod du backend [pdr-0047-go-and-tool-versions-pinned] ; openai-go v3.90.0 et a2a-go v2.7.0 dans le go.mod.

Architecture agentique · pdr-0036

L'orchestrateur et les agents A2A

Catalogue : Indicateur clé Courbe de tendance Sentiment des avis Checklist go/no-go Barre d'actions Liste des crashs

pdr-0036 · pdr-0013 · pdr-0014 · pdr-0023 · pdr-0037 · pdr-0050 · pdr-0060 · pdr-0074 · [ma-target-architecture] · [rt-gpt-live-delegation]

L'agent vocal gpt-live-1 est l'unique interlocuteur ; tout travail passe par une seule délégation vers l'orchestrateur [ma-target-architecture] [rt-gpt-live-delegation]. Voix « brise », instructions rédigées pour la démo [pdr-0037-voice-brise-delegated-instructions]. L'orchestrateur planifie la demande en tâches, choisit visiblement les agents utiles, et les appelle en parallèle [pdr-0013-orchestrator-visible-agent-selection]. Les agents sont de vrais serveurs A2A, un processus chacun ; chacun produit l'A2UI de ses surfaces, et l'orchestrateur valide contre le catalogue puis relaie sans recomposer [pdr-0036-real-a2a-agents-produce-a2ui]. La composition se fait par un LLM guidé par des exemples d'écrans attendus, sur catalogue fermé ; c'est une voie intermédiaire entre un LLM libre et des écrans pré-écrits [pdr-0023-example-guided-composition]. Livrée par 012 : un petit modèle OpenAI, gpt-6-luna, choisit composants et paramètres dans un plan structuré, les valeurs viennent du jeu de données, et toute erreur retombe sur la composition déterministe [pdr-0060-small-openai-text-model-guided-a2ui] [p-ar-llm-composer]. Seul l'agent Qualité l'utilise, parce qu'il a trois composants possibles ; Voix du client et Livraison n'en ont qu'un et restent déterministes [pdr-0074-012-llm-composer-gateway-crashlist-details]. Le catalogue a six composants [pdr-0014-six-component-catalog] ; la Liste des crashs n'apparaît que si on la demande [p-fn-screen]. Dans Genesis Canvas, les clics reviennent à l'orchestrateur comme actions typées et ne sont pas exécutés localement ; c'est un choix du projet [genui-a2ui-security] [p-ar-security], GenUI permettant aussi des actions locales ; le mécanisme, UserActionEvent puis onSubmit, est décrit dans [genui-user-actions]. Le commentary, c'est-à-dire le texte que l'orchestrateur fait dire à la voix, suppose le mode de délégation client [rt-gpt-live-delegation] : c'est le mode retenu après le spike SP-02 [pdr-0050-gpt-live-client-delegation-recommended]. Pendant que les agents travaillent, la voix ne dit que des commentaires génériques, puis le vrai résumé [ma-filler-acknowledgements] [ma-real-tool-results].

p-ar-security · pdr-0041 · pdr-0030 · pdr-0007 · pdr-0053 · pdr-0074 · [genui-a2ui-security] · [ma-prompt-injection-tools]

On a appliqué à la démo les règles habituelles : aucune clé OpenAI ni secret d'agent ne vit dans l'app, ce qu'un test vérifie [p-ar-security] [rt-ephemeral-keys]. NFR-09 parle de jeton éphémère ; pour GPT-Live, aucun n'est documenté, d'où le relais SDP par le backend [rt-gpt-live-webrtc-session]. Depuis le composeur LLM de 012, les agents n'ont pas non plus de clé : ils sont sur un réseau compose interne, sans port publié ni sortie réseau, et n'atteignent le modèle que par la passerelle de l'orchestrateur [pdr-0074-012-llm-composer-gateway-crashlist-details]. Dans notre cas, le risque principal est financier et réputationnel : un quota brûlé ou un contenu inattendu à l'écran. Les données, elles, sont toutes fictives. Les services n'écoutent que sur 127.0.0.1, sans authentification utilisateur, décision du 29 octobre [pdr-0041-backend-in-this-repo-local-no-auth] ; le backend contrôle aussi l'en-tête Host contre le DNS rebinding, limite le débit de la route de relais, et, sur les routes du canevas, refuse un POST qui porte un en-tête Origin, signe d'une page web [p-ar-security]. Le budget total est de 20 € pour tous les modèles [pdr-0030-llm-budget-20-eur]. Si le backend était un jour exposé, on reviendrait à des JWT vérifiés par JWKS. L'UI produite par un agent est validée deux fois, par l'orchestrateur puis par l'app, contre un catalogue fermé [pdr-0053-client-side-a2ui-validation-from-007] ; l'apparence vient du thème de scène, et le style proposé par l'IA est ignoré [genui-a2ui-security] [pdr-0007-closed-catalog-stage-theme]. Les extraits d'avis peuvent porter une injection indirecte : les retours d'agents sont encadrés comme données et la voix ne reçoit qu'un résumé produit par l'orchestrateur [ma-prompt-injection-tools]. Un risque vu en répétition : une voix dans la pièce, sans rapport avec la release, a obtenu une réponse de l'IA. Le porteur a décidé que l'IA doit l'ignorer [pdr-0081-rail-in-replay-and-ignore-stray-speech] ; le moyen sera conçu par la fonctionnalité 016, pas encore faite [product/sources/2026-10-31-repetition-micro.md].

SP-03 vérifié pdr-0045 : WSS maison, genui_a2a hors de l'app

specs/001-sp-03-a2a-go-genui · p-rm-spikes · pdr-0045 · [proto-a2a-go-v03-compat] · [genui-a2a-connector] · [genui-test-a2a-roundtrip]

Question du spike : un agent Go écrit avec a2a-go v2 peut-il streamer de l'A2UI vers genui_a2a côté Flutter ? Réponse vérifiée le 29 octobre : oui [specs/001-sp-03-a2a-go-genui]. Le point délicat : genui_a2a 0.10.1 parle A2A v0.3, message/stream. Le handler natif v1.0 d'a2a-go ne connaît pas les méthodes v0.3 : -32601 « method not found » sur message/stream, et -32009 sur SendStreamingMessage sans en-tête A2A-Version ; il faut monter le handler de compatibilité a2acompat/a2av0 [proto-a2a-go-v03-compat] [genui-a2a-connector]. Résultat : l'agent émet cinq événements SSE, de task submitted à completed en passant par createSurface, updateComponents et updateDataModel ; l'app rend la surface, le tap repart par connectAndSend et l'agent répond « validé ». Il n'a pas fallu de code d'adaptation supplémentaire [genui-test-a2a-roundtrip]. Pour être précis sur la portée : c'est prouvé par un test widget de bout en bout contre l'agent Go réel, processus et HTTP/SSE réels, mais avec un tap simulé, sur un client Flutter jetable ; ce n'est pas encore dans l'app. Deux autres points à connaître : sendEvent n'atteint jamais le flux du connecteur, les clics doivent passer par connectAndSend ; l'Agent Card perd url et preferredTransport si l'interface n'est pas déclarée en version 0.3. Le risque technique est donc levé. J'ai ensuite choisi, le 29 octobre, un WebSocket maison entre l'app et le backend : genui_a2a est compatible, mais il n'entre pas dans la stack de l'app ; ce spike reste la preuve qu'un client A2A Flutter pourrait parler à nos agents Go [pdr-0045-app-backend-channel-wss-recommended].

Pour conclure, six points que je retiendrais de ce projet. GenUI et A2UI : l'agent décrit l'interface sous forme de données déclaratives, au format A2UI v0.9, et c'est l'application Flutter qui la rend avec son propre catalogue de widgets [genui-overview]. La voix temps réel : un modèle voice-to-voice, ici gpt-live-1, en WebRTC ; la clé OpenAI reste côté backend, qui relaie la création de la session [rt-gpt-live-overview] [rt-ephemeral-keys]. Les agents : la voix délègue en un seul point à un orchestrateur, qui s'appuie sur des agents A2A spécialisés ; ce sont eux qui produisent l'A2UI des écrans [ma-target-architecture] [pdr-0036-real-a2a-agents-produce-a2ui]. La sécurité : l'injection de prompt reste possible ; dans ce projet, on a cherché à la limiter avec un catalogue fermé, une validation par l'orchestrateur et des retours d'agents traités comme des données non fiables, en y pensant dès la conception [p-ar-security]. La méthode : une base de connaissances vérifiée et des skills, pour que les agents de code travaillent sur des API récentes ; des mocks aux frontières, et au plus un essai réel par fonctionnalité.
